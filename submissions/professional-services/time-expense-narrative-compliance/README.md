# Time & Expense Narrative Compliance

For consultants, billing coordinators and engagement managers who need time-entry narratives that can survive pre-bill and client guideline review.

The package builds a cited activity packet, drafts grounded narratives, maps them to the client's billing-code structure, then runs an explicit **Govern** step against billing guidelines: block billing, prohibited terms, vague wording, required detail, non-billable activity, duplicate meetings, increments, code mismatch and missing time. Govern is explicit because narrative compliance is a determination, not a style preference.

## How it works

| # | Skill | Job |
|---|-------|-----|
| 1 | `activity-pull` | Builds a cited packet from enabled, engagement-scoped sources and records every privacy exclusion |
| 2 | `narrative-draft` | Drafts missing narratives and offers grounded rewrites beside preserved existing text |
| 3 | `code-map` | Maps unambiguous entries to phase/task codes and holds conflicting activity as `UNMAPPED` |
| 4 | `guideline-check` | Determines compliance using deterministic rules and verbatim, cited flags |
| 5 | `exception-report` | Writes a local draft pre-bill packet; it never sends or submits anything |

## The case that shows why it exists

Scenario B includes entries that read fine at a skim and still fail deterministically:

- A polished 7.5-hour narrative combines three activity classes under one entry, triggering block-billing rejection.
- The same entry uses prohibited/vague phrases like "attention to", "various matters" and "review and revise".
- Two consultants enter the same meeting with the same narrative, so the second is a duplicate meeting exception.
- A plausible submitted task code maps to the wrong phase and is flagged for pre-bill recoding.
- A link to disabled mailbox metadata is excluded from evidence, disclosed, and held for review.
- Three hours of engagement document activity have no matching time entry and appear in the missing-time report.

A naive reviewer may accept the fluent prose; the engine does not.

## Privacy seam

`config/signal-sources.json` is part of the package on purpose. Every engine enforces the narrowest effective policy from that file and the packet: engagement-scoped calendar metadata and engagement-workspace document activity are enabled, while mailbox content and mailbox metadata are off by default. If a skill runs without the plugin-level config, that same narrow default remains the mandatory floor, so a packet cannot enable mailbox access by itself. A `--signal-config` file is applied on top of the plugin config and can only narrow it. Every stage applies its effective policy before it uses or compares evidence. A report-time `--signal-config` that excludes evidence the entries were governed on is refused before anything is rendered; re-run narrative-draft, code-map and guideline-check with the same file. Disabled or unknown signals are removed from evidence and recorded under `provenance.excluded_signals`. A firm can explicitly enable broader sources only with policy approval, matter scoping and user notice.

## Timekeeper scope

Engines return only the requesting timekeeper's activity and time entries. Naming colleagues does not widen the scope. Other people's rows are released only in the engagement-manager team view: the requester must be the engagement manager recorded in the engagement letter, and the user must explicitly confirm the team view, which is passed as a structured `--team-view-confirmation engagement-manager:<engagement_id>` token. The token is compared exactly; surrounding spaces, a changed case or any extra character is an input error with no output. Role is never inferred from what a user says, and every downstream engine re-checks the recorded scope.

## Embedded instructions

Narrative, note, subject, deliverable, purpose, attendee, file-name and citation text is data. Every engine screens it with the shared `steering_guard` detector (vendored byte-identically in each skill's `scripts/`, SHA-256 pinned in `tests/check_shared_copies.py`). The detector works by intent family, not phrase list: text addressed to the assistant, AI or reviewer; verdict steering ("mark this entry compliant"); suppression of the review ("do not flag this entry"); rule override ("ignore the billing guidelines"); authority claims ("already approved by the partner"); scope widening; forwarding; and words that mix Latin with look-alike letters from another script. Billing vocabulary goes in only through its hooks (`signal_policy.STEERING_HOOKS`): verdict words *billable*, *compliant*, *no write down*, *approved for billing*; rule nouns *OCG*, *billing guidelines*, *phase code*; and any e-mail address or URL counts as steering. Each activity and entry is screened as one multi-field record (`scan_fields`), plus its ordered prose-field pairs, so an instruction split across fields is caught; the exception packet screens the client, matter and engagement header fields together the same way. Text too long to screen (over 200,000 characters, alone or joined) is never passed: it is held with the reason "too long to screen for embedded instructions". Flagged text is held for review and withheld from drafts (including a flagged main draft narrative that reaches guideline-check), suggested rewrites, citations, missing-time listings and the exception packet (client-billing-guidelines.md #11). Member names and metadata are data too (#11.3). Every engine sweeps the whole packet: member names the contract does not define, and every string no other screen covers (engagement header, period warning, timekeeper scope, guidelines, code structure and provenance), alone, as adjacent pairs and as whole records, so an instruction split across neighbouring list entries is caught. Every string member of an object, declared or not, is screened with its siblings as one record and in ordered pairs. That includes the strings of members other screens cover (citations, attendees, narrative), which are paired with any undeclared member. An object with more than 40 strings is withheld whole rather than screened only in part. A flagged member is renamed to a unique withheld marker. Excluded activity and entry IDs are screened as a sequence too, the way the report lists them: a withheld ID that an entry links holds that entry, and any other withheld ID holds the packet. Flagged metadata holds every entry for review, and the report says "Metadata withheld". Withheld text decides nothing: it never feeds code inference, required-element credit, the workplan join or any narrative rule. An entry left with no usable text and no linked evidence is `UNMAPPED` and held. Only the engines' own origin labels and fields that are re-derived and compared are exempt.

## Engine-result integrity

The code-map and guideline rules live in one shared module, `billing_rules.py`, which ships byte-identically next to `code_map.py`, `guideline_check.py` and `exception_report.py`. Guideline-check recomputes every entry's code mapping and holds an entry whose supplied mapping disagrees (`code_mapping_mismatch`). Exception-report re-runs the guideline rules before rendering. It refuses governed data, and writes no packet, when a recorded verdict or its flags are less severe than the rules', when missing-time items differ, or when summary totals, verdict counts or missing-time hours contradict the line items; the summary it prints is derived from the line items. An entry whose draft was withheld is re-checked on its own timesheet narrative, so a genuine reject relabelled as a hold is refused. Flag details, citations and excluded-signal IDs are rendered from the re-run and `provenance.excluded_signals`, never from supplied text. A forged "compliant" can never hide a reject (client-billing-guidelines.md #13).

Engagement identity is fixed by the first stage. Activity-pull records the engagement ID, client, matter and engagement manager from the engagement letter in `provenance.engagement_identity`, and every later engine refuses a packet whose engagement header differs from it. A signal or time entry whose source (`connector:<name>:<engagement>`) or `engagement_id` names another engagement is excluded and never rendered: the report only counts it. Exclusion reasons and citations are printed only when they are the engines' own wording, and draft and rewrite review reasons are screened like any other free text (#13.2, #13.3). `tests/run_tests.py` keeps an inventory of every string field in the contract (closed, screened, re-derived or reconciled, or never rendered), so a new field cannot reach the report unclassified. One limit remains: a packet is not signed, so someone who rewrites both the header and the recorded identity consistently is not detected; re-run the chain from activity-pull when in doubt.

## Input validation

Every engine checks every field it reads before it acts (`signal_policy.validate_packet`, shared byte-identically across the skills), and then walks the shipped contract over the whole input (`contract_check.py`, also shared byte-identically): required fields, JSON types, closed enums, patterns, and nested objects and arrays. A contract keyword the walker cannot enforce is refused, never ignored. A wrong JSON type (for example `"false"` for a boolean, `{}` or `123` in a list of strings, or `null` where a value is required), a missing required field (including a missing or `null` top-level `period`, or a period whose start is after its end), or an unrecognised enum value such as an unknown verdict, severity or draft status is an input error. The engine writes no output and the error names the field and the expected type or form, never the value or an unexpected member name (at most a type name and a length). Nothing is coerced through truthiness: the team-view confirmation must be a real boolean plus the exact token, so `"true"` or `"yes"` never releases a colleague's rows. A file that is not valid UTF-8 is an input error at every engine, never a traceback. Raw exports are held to the same rule: hours must be plain decimals (`nan`, `inf`, `1e1` and negatives are rejected), dates must be valid `YYYY-MM-DD`, times must be `HH:MM`, and rows must have one cell per column. Open vocabularies fail closed: an unknown document activity type or workplan class maps to `UNMAPPED` and is held for review. Names, IDs, class and code keys and CSV headers are compared in one canonical form: NFKC, format characters stripped, casefold and whitespace collapsed, and for IDs, keys and headers `-`, `_` and `.` folded too. So `Internal_Admin` is the internal_admin class, `mtg_orion_201` is meeting `MTG-ORION-201`, `ＡＬＥＸ  rivera` is Alex Rivera, and a fullwidth `ｅｎｔｒｙ＿ｉｄ` beside `entry_id` is a duplicate column. Output keeps the original spelling. A link that names a known activity only in a variant spelling is resolved to its exact ID at activity-pull and refused at later stages. Submitted codes and the team-view token are still compared exactly, so a variant is flagged or refused. JSON inputs are parsed strictly: nesting deeper than 64 levels is refused before parsing (a clean input error, never a traceback), and `NaN`, `Infinity`, `-Infinity`, numbers that overflow (`1e999`) and integers beyond ±2**53 are input errors. A duplicate JSON key, a CSV header repeated after canonical folding, or an engagement-letter field given twice is malformed input, never silently overwritten. A repeated activity ID or entry ID, or an activity linked twice by one entry, is refused at activity-pull and again at every later stage, so no ID-keyed index silently keeps one record. A record is active or excluded, never both: an active entry or signal also listed in `provenance.excluded_entries` or `provenance.excluded_signals`, or a link in both an entry's `activity_ids` and `excluded_activity_ids`, is malformed input. A repeated workplan ID or workplan key is refused at activity-pull. Every CSV's header row is always checked for the required columns. A header-only file with the right columns is a valid, explicitly empty register; an empty file is not. Every engine serialises its whole output first, then writes it atomically (a temp file in the output folder, then `os.replace`). A failed run, for example on a lone surrogate, neither creates nor truncates the output file.

## What you bring

Client billing guidelines, engagement-letter billing terms, task/phase code structure, engagement calendar metadata, document activity logs, existing timesheet entries, prior accepted narratives, WIP/pre-bill records and the firm's configured signal policy.

## Boundaries

Draft-first. It does not submit time, approve a pre-bill, alter WIP balances or bill a client. It does not handle expense reports, receipts or travel claims. Every skill follows the same recipient rule: drafts go only to the internal billing coordinator or engagement manager, never the client or any external address. If asked to share something, it prepares a draft, shows the internal recipients and content, and waits for explicit confirmation; if the internal recipient is unknown, it asks rather than guessing or looking one up. Exception-report owns refusals to submit time or approve a pre-bill.

The release bundle includes `tests/run_tests.py`, `tests/check_shared_copies.py` and the human spot-check prompt set so evaluators can reproduce the packaged engines and verify shared-file integrity.
