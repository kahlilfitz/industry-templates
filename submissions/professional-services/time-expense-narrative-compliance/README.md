# Time & Expense Narrative Compliance

For consultants, billing coordinators and engagement managers who need time-entry narratives that can survive pre-bill and client guideline review.

The package builds a cited activity packet, drafts grounded narratives, maps them to the client's billing-code structure, then runs an explicit **Govern** step against billing guidelines: block billing, prohibited terms, vague wording, required detail, non-billable activity, duplicate meetings, increments, code mismatch and missing time. Govern is explicit because narrative compliance is a determination, not a style preference.

## How it works

| # | Skill | Job |
|---|-------|-----|
| 1 | `activity-pull` | Builds a cited packet from enabled, engagement-scoped sources and records every privacy exclusion |
| 2 | `narrative-draft` | Drafts missing narratives and offers grounded rewrites beside preserved existing text |
| 3 | `code-map` | Maps unambiguous entries to phase/task codes and holds conflicting activity as `UNMAPPED` |
| 4 | `guideline-check` | Determines compliance using deterministic rules and verbatim, cited flags |
| 5 | `exception-report` | Writes a local draft pre-bill packet; it never sends or submits anything |

## The case that shows why it exists

Scenario B includes entries that read fine at a skim and still fail deterministically:

- A polished 7.5-hour narrative combines three activity classes under one entry, triggering block-billing rejection.
- The same entry uses prohibited/vague phrases like "attention to", "various matters" and "review and revise".
- Two consultants enter the same meeting with the same narrative, so the second is a duplicate meeting exception.
- A plausible submitted task code maps to the wrong phase and is flagged for pre-bill recoding.
- A link to disabled mailbox metadata is excluded from evidence, disclosed, and held for review.
- Three hours of engagement document activity have no matching time entry and appear in the missing-time report.

A naive reviewer may accept the fluent prose; the engine does not.

## Privacy seam

`config/signal-sources.json` is part of the package on purpose. Every engine enforces the narrowest effective policy from that file and the packet: engagement-scoped calendar metadata and engagement-workspace document activity are enabled, while mailbox content and mailbox metadata are off by default. If a skill runs without the plugin-level config, that same narrow default remains the mandatory floor, so a packet cannot enable mailbox access by itself. A `--signal-config` file is applied on top of the plugin config and can only narrow it. Every stage applies its effective policy before it uses or compares evidence. A report-time `--signal-config` that excludes evidence the entries were governed on is refused before anything is rendered; re-run narrative-draft, code-map and guideline-check with the same file. Disabled or unknown signals are removed from evidence and recorded under `provenance.excluded_signals`. A firm can explicitly enable broader sources only with policy approval, matter scoping and user notice.

## Timekeeper scope

Engines return only the requesting timekeeper's activity and time entries. Naming colleagues does not widen the scope. Other people's rows are released only in the engagement-manager team view: the requester must be the engagement manager recorded in the engagement letter, and the user must explicitly confirm the team view, which is passed as a structured `--team-view-confirmation engagement-manager:<engagement_id>` token. The token is compared exactly; surrounding spaces, a changed case or any extra character is an input error with no output. Role is never inferred from what a user says, and every downstream engine re-checks the recorded scope against the raw engagement letter and exports (`--raw-dir`, default `raw/` next to the activity packet). Whenever `--raw-dir` is given, and always for a team view, each engine re-runs activity-pull's own code on those exports and refuses an activity packet that is not exactly the result (#12.1, #13.8). A time entry's evidence is only its own timekeeper's activity (#12.2). In the team view, a link from one person's entry to an activity recorded for another person is not evidence: it is not drafted from, mapped or counted, and the entry is held (`cross_person_link`, which counts the links without naming the other person). Every later engine refuses a packet whose active link crosses people. Names compare in canonical form, so a variant spelling of the same person is the same person. A shared meeting is evidence for each attendee through their own calendar record.

## Embedded instructions

Narrative, note, subject, deliverable, purpose, activity class, attendee, file-name, ID and citation text is data. Every engine screens it with the shared `steering_guard` detector (vendored byte-identically in each skill's `scripts/`, SHA-256 pinned in `tests/check_shared_copies.py`). The detector works by intent family, not phrase list: text addressed to the assistant, AI or reviewer; verdict steering ("mark this entry compliant"); suppression of the review ("do not flag this entry"); rule override ("ignore the billing guidelines"); authority claims ("already approved by the partner"); scope widening; forwarding; and words that mix Latin with look-alike letters from another script. Billing vocabulary goes in only through its hooks (`signal_policy.STEERING_HOOKS`): verdict words *billable*, *compliant*, *no write down*, *approved for billing*; rule nouns *OCG*, *billing guidelines*, *phase code*; and any e-mail address or URL counts as steering. Each activity and entry is screened as one multi-field record (`scan_fields`), plus its ordered prose-field pairs, so an instruction split across fields is caught; the activities one entry links are also read together, each supplied field (activity class included) down the activities in link order; the exception packet screens the client, matter and engagement header fields together the same way. The rendered report is screened as printed: every table cell, bullet and data line, IDs, row references and citations included, alone, by column and row, and in reading order across row, bullet and section boundaries, so an instruction split between one section's last value and the next section's first ID is withheld. It is also read down the whole report as one sequence of lines, across sections, in runs of up to 8 consecutive lines and as a whole, so a split over three or more lines is withheld; punctuation-only filler lines and values are skipped, never counted. Only the report's fixed title, headings and table headers, which hold no data, are skipped (`exception_report.FIXED_LINES`), and `tests/run_tests.py` fails if the renderer adds a line outside those structures. Text too long to screen (over 200,000 characters, alone or joined) is never passed: it is held with the reason "too long to screen for embedded instructions". Flag details and review reasons that an engine composes from more than one supplied value (the activity classes in a block-billing or unmapped-code detail, the IDs in a date-mismatch, duplicate-meeting, excluded-link or uncovered-activity text, a submitted code) are screened before the values are joined: each value, every run of neighbouring values and all of them in the order the text joins them (`signal_policy.composed_hits`), then the composed text itself. When they trip, the detail gives counts only ("activity class names not shown: flagged as embedded_instruction when read together") and the entry gets an `embedded_instruction` hold, so `governed.json` is safe to quote on its own; the supplied values stay only as data in `activity_signals`. Flagged text is held for review and withheld from drafts (including a flagged main draft narrative that reaches guideline-check), suggested rewrites, citations, missing-time listings and the exception packet (client-billing-guidelines.md #11). Member names and metadata are data too (#11.3). Every engine sweeps the whole packet: member names the contract does not define, and every string no other screen covers (engagement header, period warning, timekeeper scope, guidelines, code structure and provenance), alone, as adjacent pairs, as contiguous runs of up to 8 list entries and as whole records, so an instruction split across two, three or more neighbouring list entries is caught, even inside a long benign list. Every string member of an object, declared or not, is screened with its siblings as one record and in ordered pairs. That includes the strings of members other screens cover (citations, attendees, narrative), which are paired with any undeclared member. An object with more than 40 strings is withheld whole rather than screened only in part. A flagged member is renamed to a unique withheld marker. Excluded activity and entry IDs are screened as a sequence too, the way the report lists them: a withheld ID that an entry links holds that entry, and any other withheld ID holds the packet. Names are harvested before the sweep: a timekeeper or manager name withheld in any field is withheld everywhere it appears, and that person's rows are held, never dropped as another timekeeper's. Flagged metadata holds every entry for review, and the report says "Metadata withheld". Withheld text decides nothing: it never feeds code inference, required-element credit, the workplan join or any narrative rule. An entry left with no usable text and no linked evidence is `UNMAPPED` and held. Only the engines' own origin labels and fields that are re-derived and compared are exempt. Only the engines write withheld markers: raw input shaped like one (exact, embedded, fullwidth or upper-case) is refused at activity-pull, later stages refuse any marker that is not the exact one the engines emit, and a record carrying an exact marker is held, so a marker never suppresses a rule or improves a verdict.

## Engine-result integrity

The code-map and guideline rules live in one shared module, `billing_rules.py`, which ships byte-identically next to `code_map.py`, `guideline_check.py` and `exception_report.py`. Guideline-check recomputes every entry's code mapping and refuses a coded packet whose mappings differ (#13.1, #13.8); if a disagreeing mapping ever reaches the guideline rules in-process, the entry is held (`code_mapping_mismatch`). Exception-report re-runs the guideline rules before rendering. It refuses governed data, and writes no packet, when a recorded verdict or its flags are less severe than the rules', when missing-time items differ, or when summary totals, verdict counts or missing-time hours contradict the line items; the summary it prints is derived from the line items. An entry whose draft was withheld is re-checked on its own timesheet narrative, so a genuine reject relabelled as a hold is refused. Flag details, citations and excluded-signal IDs are rendered from the re-run and `provenance.excluded_signals`, never from supplied text. A forged "compliant" can never hide a reject (client-billing-guidelines.md #13).

Engagement identity is fixed by the first stage. Activity-pull records the engagement ID, client, matter and engagement manager from the engagement letter in `provenance.engagement_identity`, and every later engine refuses a packet whose engagement header differs from it. A signal or time entry whose source (`connector:<name>:<engagement>`) or `engagement_id` names another engagement is excluded by the stage that first reads it (activity-pull for raw rows, narrative-draft for the activity packet) and never rendered: the report only counts it. A time entry's link to a raw row activity-pull left out for that reason (`provenance.out_of_scope_rows`) is counted the same way, never named. Another party's record is recorded by position only (#13.10): a raw row as `calendar-export-row-N` or `document-activity-log-row-N`, a packet record as `other-engagement-signal-N`, `other-engagement-entry-N` or `other-timekeeper-signal-N`, and every in-scope link to it carries the same label. Colleagues a requester names whose rows are withheld are recorded as `other-timekeeper-name-N`, never by name. Its supplied ID is not trusted even when well-formed, and none of its fields (ID, subject, file name, meeting ID, source scope, narrative) reaches any output. A link to another timekeeper's raw row, which activity-pull never reads, reads exactly like a link to an ID that does not exist. These label forms are reserved: a supplied ID or link in one of them is refused. From the drafted stage on, a record that now names another engagement, a time entry whose source is not the timesheet connector, or a signal whose source disagrees with the raw export it cites or the connector namespace of its activity ID is an edited intermediate and is refused with no output (#13.7). Reconciliation never selects which records to compare by a field the input can edit: each entry's whole compliance object (verdict, every flag with its source, confidence, detail and citations, and the entry's source, confidence and citations) and the whole pre-bill summary must equal the re-run's, so a carried extra flag or stricter verdict the rules do not give is refused, and each exclusion record's source, policy key and writing engine must agree with its reason. The engines that may have written a record are fixed by the stage, never by the carried `provenance.engines` list. Exclusion reasons and citations are printed only when they are the engines' own wording, and draft and rewrite review reasons are screened like any other free text (#13.2, #13.3). `tests/run_tests.py` keeps an inventory of every string field in the contract (closed, screened, re-derived or reconciled, or never rendered), so a new field cannot reach the report unclassified. Link state is fixed by activity-pull (#13.4): every entry always carries `activity_ids`, `excluded_activity_ids` and `cross_person_activity_ids`, and every later engine reconciles every copy of those links exactly (the draft's linked, covered and excluded lists, each rewrite's link, the draft status, the link-derived review reasons and `needs_review`, the exclusion records, the `disabled_source_signal` and `cross_person_link` flags, the exception list's excluded links and the evidence hours). The only accepted difference is a later stage's own narrower `--signal-config` moving an active link to the excluded list, and that stage re-drafts the entry; any other partial edit is refused with no output. An evidence link must name a signal in the packet. Values the engines derive are never trusted as carried (#13.5): every later stage re-derives each signal's `billable_signal` (from its activity class) and `confidence` (from its workplan match), and each entry's whole draft (narrative, status, review reasons, confidence, citations, coverage and suggested rewrites) through the same shared drafting code narrative-draft uses (`signal_policy.derive_draft`), and refuses a packet whose carried copy differs. So a one-field edit (a non-billable flag that hides missing time, a raised confidence that drops the #9.1 hold, or a rewritten draft narrative that clears a text rule) can never relax a check. Exception-report runs its re-check on re-derived drafts too. Signal-policy settings carried in a packet can only narrow each engine's own policy. Every withheld placeholder is bound to its own hold (#11.4): the engine that places it records its exact path in a `withheld_fields` ledger, and a marker without its path, a path without its marker, or a marker on an unheld record is refused. Exclusions hold in every section (#13.6): an out-of-scope row, excluded signal, skipped source, withheld colleague or excluded entry is refused wherever another section names it; a blank key never matches another; every keyed collection is checked for duplicates in canonical form; and the exception list is reconciled item by item against the line items, not by count. One limit remains: packets are not signed, so someone who rewrites the activity packet and every later packet consistently is not detected; re-run the chain from activity-pull when in doubt.

Every stage re-derives the whole document (#13.8). Code-map, guideline-check and exception-report each take the activity packet (`--activity activity.json`) as well as the packet they transform. Before reading the carried packet, the stage re-runs every earlier engine in-process on the screened activity packet. It uses the same stage functions the engines run (`signal_policy.draft_stage`, `billing_rules.code_stage` and `govern_stage`) and the run parameters the carried packet records: the writing run's timestamp and any narrower signal policy an earlier stage applied. It then requires the carried packet to be deep-equal to the result in canonical JSON (sorted keys, exact types), covering every engine-owned field and section, provenance included (`billing_rules.check_rederived`). The only field left out is listed in `signal_policy.NOT_ENGINE_OWNED`: `provenance.generated_at`, the writing run's own timestamp, a run parameter that no input determines. It is still validated against the contract as an ISO-8601 timestamp and screened. Any missing, extra or changed field or section, including a deleted or renamed privacy exclusion in `provenance.excluded_entries`, is refused with no output. The message counts the top-level sections that differ and echoes no value, field or path. `tests/run_tests.py` walks the contract schemas and fails if any field path is neither compared nor allow-listed. The per-field checks this makes redundant have been removed (the drafted-packet draft comparison, and the per-field body of exception-report's reconciliation, which now only checks a report-time `--signal-config`). Re-running a stage on its own output, or passing a drafted, coded or governed packet or another engagement's activity packet as `--activity`, is refused.

## Input validation

Every engine checks every section and nested record it reads before it acts (`signal_policy.validate_packet`, shared byte-identically across the skills), so a wrong type (an object where a list is expected, a string where an object is expected) is an input error, never iterated or skipped. It then walks the shipped contract over the whole input (`contract_check.py`, also shared byte-identically): required fields, JSON types, closed enums, patterns, and nested objects and arrays. A contract keyword the walker cannot enforce is refused, never ignored. A wrong JSON type (for example `"false"` for a boolean, `{}` or `123` in a list of strings, or `null` where a value is required), a missing required field (including a missing or `null` top-level `period`, or a period whose start is after its end), or an unrecognised enum value such as an unknown verdict, severity or draft status is an input error. Every carried date and timestamp is checked at every stage, not only the CLI option: dates are real `YYYY-MM-DD` calendar dates, and `provenance.generated_at` (like `--generated-at`) is an ISO-8601 timestamp with seconds and an offset. The engine writes no output and the error names the field and the expected type or form, never the value or an unexpected member name (at most a type name and a length). No message or log line echoes a path or file name taken from input: each input is named by a fixed label ("activity input", "--signal-config" and so on), an OS error is reported by its reason only, and `provenance.signal_policy.policies_applied` records `--signal-config (additional)` without the file name. A member name is printed only when the contract declares it; any other member is named by position (`<member #n>`). CSV errors name the fixed export file, the declared column and the row, never a supplied header. A command-line error names only the engine's own options: any other argument error (an unknown option, a stray value, an ambiguous prefix) is a fixed message that never repeats what was typed. Nothing is coerced through truthiness: the team-view confirmation must be a real boolean plus the exact token, so `"true"` or `"yes"` never releases a colleague's rows. A file that is not valid UTF-8 is an input error at every engine, never a traceback. Every contract object with fixed properties has a `required` array covering every field a later stage renders or relies on, and display fields such as a missing-time subject cannot be null. The engagement letter is read one labelled line at a time (`- <field>: <value>`, split on every line boundary including U+2028), and only from its one `## Engagement` section: a blank labelled field is an input error, never filled from the next line, and any other non-blank line in that section, a declared field outside it, or a missing or repeated section is refused (#8.4). Every ID is a record ID (#13.9): 1 to 64 ASCII letters or digits in segments joined by single `-`, `_` or `.`, checked in the engagement letter, in every raw ID cell and link (exactly as written, so a padded cell is refused) and in every contract field named `*_id`, `*_ids` or `*_code` at every stage. A member the contract does not declare but whose name marks an ID (`review_id`, `reviewId`, `evidence_ids`, at any depth, and in a `--signal-config` file) is held to the same rule: a number, boolean, object, nested array or prose there is refused with its field path, never only walked; prose, spaces, commas and other punctuation in an ID are refused with an error that names the row or field and never the value. A JSON `*_ids` member, declared or not, is an array or null: a string, number, boolean or object is refused with its path and its JSON type. In the timesheet CSV, `activity_ids` is a `;`-separated list: spaces around each link and empty items (`;;`, a trailing `;`) are skipped, and every remaining item must be an ID. Invalid dates and timestamps are named the same way (contract path, file, row and column, or command-line option), never by value. A well-formed ID is still screened as text wherever it is printed. Raw exports are held to the same rule: hours must be plain decimals (`nan`, `inf`, `1e1` and negatives are rejected), dates must be valid `YYYY-MM-DD`, times must be `HH:MM`, and rows must have one cell per column. Open vocabularies fail closed: an unknown document activity type or workplan class maps to `UNMAPPED` and is held for review. Names, IDs, class and code keys and CSV headers are compared in one canonical form: NFKC, format characters stripped, casefold and whitespace collapsed, and for IDs, keys and headers `-`, `_` and `.` folded too. So `Internal_Admin` is the internal_admin class, `mtg_orion_201` is meeting `MTG-ORION-201`, `ＡＬＥＸ  rivera` is Alex Rivera, and a fullwidth `ｅｎｔｒｙ＿ｉｄ` beside `entry_id` is a duplicate column. Output keeps the original spelling. A link that names a known activity only in a variant spelling is resolved to its exact ID at activity-pull and refused at later stages. Submitted codes and the team-view token are still compared exactly, so a variant is flagged or refused. JSON inputs are parsed strictly: nesting deeper than 64 levels is refused before parsing (a clean input error, never a traceback), and `NaN`, `Infinity`, `-Infinity`, numbers that overflow (`1e999`) and integers beyond ±2**53 are input errors. A duplicate JSON key, a CSV header repeated after canonical folding, or an engagement-letter field given twice is malformed input, never silently overwritten. A repeated activity ID or entry ID, or an activity linked twice by one entry, is refused at activity-pull and again at every later stage, so no ID-keyed index silently keeps one record. A record is active or excluded, never both: an active entry or signal also listed in `provenance.excluded_entries` or `provenance.excluded_signals`, or a link in both an entry's `activity_ids` and `excluded_activity_ids`, is malformed input. A repeated workplan ID or workplan key is refused at activity-pull. Every CSV's header row is always checked for the required columns. A header-only file with the right columns is a valid, explicitly empty register; an empty file is not. An unrecognised line is refused, never skipped (#8.4): a CSV row naming no timekeeper (empty cells, a lone `TBD`, a comment line) is refused in every timekeeper scope, and a workplan row with no engagement, an item type other than `calendar_event` or `document`, or a blank match key is refused rather than left unindexed, by activity-pull, every re-deriving stage and the team-view check. Missing is never empty (#8.3): an absent, zero-byte or unreadable export or engagement letter, a missing required column or labelled field, a missing, zero-byte, `null`, `{}`, `[]` or `""` JSON input or `--signal-config`, and a plugin `config/signal-sources.json` that is zero-byte, `null`, `{}` or has a null or non-object `sources` or source entry are refused with no output, by activity-pull and by every later stage that re-derives from the same input (they re-run activity-pull's own code). An absent plugin config means the documented narrow default floor, recorded as `narrow default` in `policies_applied`; an empty `sources` object disables every source. A packet with no time entries and no activity signals carries a `period_check` warning (with or without a requested period), and the exception report then states "No data" and reports the verdicts as "none (no time entries)" rather than rendering a clean page. `mailbox-summary.txt`, `client-billing-guidelines-extract.md` and `code-structure.md` in `raw/` are not engine inputs: the rules and code structure come from the plugin's own references and constants, and mailbox sources are disabled (a present mailbox export is only recorded as skipped, unopened), so their absence changes no verdict. Every engine serialises its whole output first, then writes it atomically (a temp file in the output folder, then `os.replace`). A failed run, for example on a lone surrogate, neither creates nor truncates the output file.

## What you bring

Client billing guidelines, engagement-letter billing terms, task/phase code structure, engagement calendar metadata, document activity logs, existing timesheet entries, prior accepted narratives, WIP/pre-bill records and the firm's configured signal policy.

## Boundaries

Draft-first. It does not submit time, approve a pre-bill, alter WIP balances or bill a client. It does not handle expense reports, receipts or travel claims. Every skill follows the same recipient rule: drafts go only to the internal billing coordinator or engagement manager, never the client or any external address. If asked to share something, it prepares a draft, shows the internal recipients and content, and waits for explicit confirmation; if the internal recipient is unknown, it asks rather than guessing or looking one up. Exception-report owns refusals to submit time or approve a pre-bill.

The release bundle includes `tests/run_tests.py`, `tests/check_shared_copies.py` and the human spot-check prompt set so evaluators can reproduce the packaged engines and verify shared-file integrity.

Run the tests from the plugin root with `python3 tests/run_tests.py`. Each result prints as it runs (`PASS <label>` or `FAIL <label>  (detail)`, under an `== group <name>` header). Failures are repeated under `== failures`, the last line is `N/M checks passed`, and the exit code is 1 on any failure. `--list-groups` prints the group names. `--group NAME` (repeatable) runs only those groups, plus any earlier group whose state they read (`qa13_tests` also runs every `defence_in_depth` group and `qa12_tests`; `drqg14_tests` also runs five groups whose rendered reports its coverage check scans). An unknown group or argument exits 2.
